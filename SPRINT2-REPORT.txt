DESIGN SUMMARY 1 — PORTAL AUTH SESSION MODEL (Part A)
================================================================================
IDENTITY vs DB-ROLE SPLIT. Patient identity = Supabase Auth (GoTrue), httpOnly
sb-* cookies via @supabase/ssr (repo convention). A patient auth user has NO
public.users row and NO org, so get_user_organization_id()/get_user_role() return
NULL and the clinician `TO authenticated` policies fail closed for patients by
construction.

DB ACCESS RUNS AS THE patient_portal POSTGRES ROLE (not a Supabase client —
those only bind anon/authenticated/service_role). src/lib/portal/portal-db.ts
opens a pg connection as patient_portal (PORTAL_DATABASE_URL — PRD-02's "portal
uses the patient_portal role's connection string"), injects the patient's
auth_user_id as request.jwt.claims.sub (+ SET LOCAL ROLE patient_portal), and the
already-proven `TO patient_portal` RLS scopes every row. This is the identical
mechanism the DB tests exercise. The GoTrue cookie only authenticates identity
(resolvePortalPatient -> getPortalPatientMapping); the write executes over the
portal connection. NEVER the service role for patient writes (S4).

REJECTED ALTERNATIVE: a GoTrue custom access-token hook stamping
role: patient_portal (so a normal Supabase client would role-switch). It needs
GRANT patient_portal TO authenticator + a prod-only auth hook (untestable in the
isolation harness) and couples identity to DB-role at the token layer. The
connection-string design keeps the concerns separate, is PRD-mandated, and is the
proven test path. (Documented in SCHEMA-NOTES.)

FLOWS: POST /api/portal/claim (validate SHA-256 token -> admin.createUser
{email_confirm:true} -> link patient_portal_users -> mark invite claimed ->
signInWithPassword + applyCookies); POST /api/portal/login; the [token] page
authenticates (session+patient -> intake; no session+valid token -> account form;
used token -> sign-in; expired/invalid -> clear error). CSRF (validateOrigin),
fail-closed rate limits (invitationAccept/login), INTAKE_V1-gated (404).

TEMPLATE-AWARE VALIDATION (deferred from P2, now live): at write time the route
loads the SELECTED template through the patient_portal role (active system/own-org
catalog read — no service role), then validateResponsesAgainstTemplate allowlists
response keys against the template's sections/fields and coerces per field type,
layered on the template-independent IntakeWriteSchema. The coerced, allowlisted
responses are what get persisted.

DESIGN SUMMARY 2 — CHILD-ROW MATERIALIZATION (Part B)
================================================================================
CHOICE: a SECURITY DEFINER RPC public.portal_submit_intake(uuid) owned by the
system, NOT patient-role INSERTs.

JUSTIFICATION against the RLS design:
 * The whole materialize-then-submit is ONE server-enforced, atomic, idempotent
   unit — immune to app-layer partial failure and to the submit-lock timing
   (submitted_at IS NOT NULL closes patient child writes). Patient-role INSERTs
   would need multi-statement app orchestration racing its own submit lock.
 * It mirrors the existing SM-2 pattern (signed_snapshot is already built in SQL);
   materialization is the same responses-JSONB -> normalized-rows transformation
   and belongs beside it, enforced once regardless of caller.
 * SAFETY (B0 lesson): REVOKE ALL FROM PUBLIC + explicit REVOKE EXECUTE FROM
   anon/authenticated/service_role; EXECUTE granted ONLY to patient_portal;
   search_path pinned to public; and — because DEFINER bypasses RLS — an explicit
   auth.uid() OWNERSHIP guard in the body (a caller can only materialize its own
   submission). Role-escape DB tests confirm authenticated/anon get
   "permission denied".

MAPPING (from the real family_medicine template): pmh.problems->problems,
medications.medications->medications, allergies.{nkda,allergies}->allergies
(NKDA => one nkda=true row, allergen rows suppressed), family_history->
family_history, social_history.*->social_history (1 row), ros.<system>->
ros_responses (per answered system), immunizations->immunizations. All rows:
source='patient', reconciled=false, intake_submission_id set, created_by=NULL.
Code-less rows flagged needs_coding (problems/medications/allergies) or NULL code
(family/immunizations). psh.surgeries, vitals, demographics, consents have no
target table and stay in responses JSONB.

 * IDEMPOTENT: guarded by materialized_at — a re-submit returns existing counts,
   inserts nothing (proven).
 * ROLLBACK: a malformed clinical value (out-of-range ROS finding) RAISEs and the
   whole call rolls back — no partial rows, submitted_at stays NULL (proven).

MISMATCHES / NOTES (reported, not guessed)
================================================================================
1. NOTE MODEL RESISTS DISCRETE STRUCTURED SECTIONS. clinical_notes is SOAP-only
   (subjective/objective/assessment/plan + one `content` blob) — NO discrete
   PMH/PSH/meds/... columns and NO JSONB sections. Per the prompt ("report if the
   note model resists rather than forcing it"), I did NOT add a dead column;
   the structured sections render as markdown into `content` with subjective
   (history) + assessment (reconciled problem list) pre-filled, DRAFT status. If
   first-class structured note sections are wanted later, that is a separate note-
   model change (additive JSONB column + editor support).

2. FM SEED CONSENTS ARE BARE BOOLEANS (type:"boolean"), not the `consent`-type
   ConsentValue object. Template-aware validation accepts BOTH forms; the boundary
   schema's consent enforcement (isConsentShaped) only fires for the object form,
   as before. No change forced.

3. snomed / cvx CODE BINDINGS HAVE NO TERMINOLOGY SOURCE. The FM template binds
   psh->snomed, family_history->snomed, immunizations->cvx, but the terminology
   proxy serves only rxnorm/icd10/allergen. Those groups arrive code-less
   (code:null) and are materialized with needs_coding / NULL code, flagged for
   provider resolution — consistent with P2's documented degrade-to-free-text.

4. THE RPC IS THE APP'S SUBMIT PATH; the RLS submitted_at capability is unchanged.
